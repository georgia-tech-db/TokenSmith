# 50-page DB textbook chunking experiment

Date: 2026-09-14. Local experiment only; no production prompt, chunker, installed app,
model files, or normal library were changed for this experiment.

Subsequent integration: the app now uses numbered-line AI preparation (version 15),
with Basic as the default for new collections. The measurements in this report remain
the original version 14 experiment, not results from the integration. A fresh production
import under `tmp/db50-numbered-production` completed all 50 pages in 123.35s with
111 chunks/96 units and exact coverage; Basic took 5.59s. No new answers were generated
in that integration check. The runner now tests production Basic/AI directly, without
the old prototype overrides.

## Conclusion

LLM-selected complete passages help some questions, but this experiment does **not**
establish a reliable overall answer-quality win over Basic preparation. Sparse-index
lookup improved on both generations. The nested-loop answer initially improved with
better evidence, but its repeat reversed the MRU eviction rule despite receiving the
same evidence. Other answers were mostly similar, sometimes longer, and several
generation errors remained. Do not promote the current AI preparation to a dependable
default on the strength of this experiment.

## Setup

- Local Database System Concepts, 7th Edition PDF, printed pages 591-640 inclusive
  (physical PDF pages 620-669): exactly 50 pages, 122,601 extracted characters.
- Coverage: variable-length records, slotted pages, multitable clustering, buffer
  management, column stores, ordered indices, and B+ tree queries. Exercises and
  figures in the selected pages were retained; no manual source repairs.
- Both successful arms have the same extracted-source SHA-256:
  `2de3594c747407b56b39e09a77972f200ce97e9a9f4184a39845dfc214fdec1b`.
- Gemma `gemma4:e4b`, Nomic `nomic-embed-text`, real production hybrid search, four
  sources, 8,192 context tokens, 1,024 answer tokens, temperature 0.7, top-p 0.4,
  top-k 40, repetition penalty 1.18. Same current production answer, rewrite, and
  suggestion services in both arms. No keyword-only accuracy runs.
- Ten identical seed questions and source-based expected facts defined before answer
  generation. Three two-follow-up chains per arm, following the first suggestion
  generated from that arm's actual preceding answer, not an unrelated fixed sequence.
- 32 initial answers plus eight repeat answers: **40 real answers**. Four seed cases
  were selected after the first run for repeat checks, without tuning anything.
- This was a direct production-service experiment, not a native GUI test. Assessment
  is a manual source-based review, not an automated LLM-judge score or CI accuracy badge.

## Preparation Arms

| Arm | Outcome | Elapsed |
| --- | --- | ---: |
| Current exact-quote AI preparation | Failed on window 2 after three rejected attempts; no index published | 31.36s |
| Experimental exact-prefix adapter | Also failed; source encoding artifacts were rewritten inside quotes | 24.53s |
| Experimental numbered-line AI preparation | All 50 pages prepared, embedded and indexed; 29 preparation calls, no retries | 138.63s |
| Basic preparation | All 50 pages prepared, embedded and indexed | 5.72s |

The successful AI arm is **not the unchanged app implementation**. It asks the same
installed model to choose explicitly numbered source lines instead of copying opening
text. A JSON schema constrains choices to existing line numbers; validation checks
ordering and uniqueness. Original source bytes are still copied by the application,
never generated by the model. This is isolated in the experiment runner.

Both early failures are retained as failures. Neither was bypassed by silently falling
back to Basic, deleting difficult pages, or publishing only successfully prepared windows.

The successful AI variant retained exact source coverage and produced 115 chunks in
102 logical units. Basic produced 165 chunks. Eight AI units contain fewer than 20
words, and some headings are running headers or sentence fragments: successful
validation does not prove good semantic boundaries.

## Answer Review

| Seed topic | Comparison |
| --- | --- |
| Variable-length attributes | Similar, correct offset/length explanation in both. |
| Multitable clustering trade-off | Both explain join locality versus fewer department tuples per block. AI is longer and leaks source labels into prose. |
| Slotted-page compaction | Both explain stable indirection through header entries; both initially leave the actual header-update step implicit. Follow-ups explain it. |
| Column-store trade-off | Both explain selective column reads, reconstruction, and compressed-update costs. No clear quality gain. |
| Nested-loop LRU/MRU | AI retrieves the complete cross-page example and initially explains MRU; Basic is vague. AI repeat explicitly says MRU keeps the most recently accessed items, reversing the rule. Not a reliable win. |
| Pinning versus LRU | Both correctly explain protection from eviction during access. AI adds the all-holders-unpin condition, a useful detail. |
| Sparse-index lookup | Consistent AI improvement: preceding entry, forward data scan, and sorted-data prerequisite. Basic answers about a sparse outer index and misses the data-file ordering requirement in both runs. |
| Secondary-index density | Unresolved in both. Answers confuse duplicate-key handling with density. Basic implies sparsity depends on a non-candidate key; AI says every possible key value on one run and introduces candidate-key confusion on repeat. |
| B+ versus binary tree | Both correctly explain high fanout and roughly four versus twenty node accesses. Basic additionally explains the cached root. |
| Range-query record fetches | Both get the main record-locality trade-off, but initially overstate physical adjacency of leaves. Repeats blur pointer retrieval with record retrieval in the random-I/O statement. Not a clean correctness win. |

For the sparse-index question, Basic's first source begins mid-sentence with "of the
search key", omitting the premise that the relation must be sorted. The AI version
includes the full dense/sparse definition at source 3. It correctly answers the question
despite also retrieving the multilevel-index discussion. This is concrete evidence that
more complete passages can help, even without improved first-source ordering.

For the nested-loop question, Basic omits the decisive MRU paragraph on printed page
608. The AI first source spans printed pages 607-609 and includes it. Nevertheless,
the repeat response states:

> MRU strategy (which keeps the most recently accessed items)

That is wrong for MRU replacement: it selects the most recently used eligible block
for eviction. The source says so explicitly. This is a generator-faithfulness failure,
not a missing-context failure. Ordered source IDs, source text, and prompt-budget
values were verified identical between the two generations for all eight repeated
arm/question pairs.

## Follow-Up Quality

The record and buffer chains mostly retain the subject and explain valid consequences.
They are sometimes repetitive. Basic's unpin answer loosely conflates eviction safety
with concurrent modification, which should be distinguished from locking.

The indexing chains reveal remaining errors. The AI suggests:

> Why are secondary index pointers often scattered on disk?

This blurs the location of index entries with the locations of their target records.
The next answer compounds the terminology, eventually saying a clustering index
prevents scattering "when used as a secondary index". More complete retrieved units
did not prevent the suggestion/answer loop from reinforcing a confused premise.

The follow-ups differ between arms by design because they depend on actual answers;
they are qualitative conversation checks, not matched accuracy measurements.

## Cost

| Measured stage | Basic | Numbered-line AI |
| --- | ---: | ---: |
| PDF extraction | 0.13s | 0.13s |
| Preparation | 0.03s | 133.48s |
| Embeddings | 5.31s | 4.82s |
| Index publication | 0.26s | 0.21s |
| Total to searchable index | **5.72s** | **138.63s** |
| First-pass median, ten matched seed responses | 10.76s | 24.27s |
| First-pass median, all 16 responses | 12.97s | 23.32s |
| Median estimated seed prompt tokens | 1,678 | 3,534 |

Extra preparation/import cost in this sample: **132.91 seconds**, about 2 minutes
13 seconds. The AI arm's larger retrieved units roughly doubled the median seed prompt
size. No sources were truncated by the prompt budget in either original run.

Response timings include retrieval, rewriting when needed, answer generation, and
suggestion generation. They are **not** a stable latency multiplier: on the four
repeated seeds, median response times were 13.66s Basic and 12.06s AI. Hardware load,
cache state and stochastic output length were not controlled. Do not attribute the
entire first-pass timing difference to chunking or extrapolate it to a full textbook.

Index timings exclude GUI work, thumbnails, process startup, and model downloads.
The installed models were reused; unchanged-boundary caches were not used for the
successful first import. These are single import measurements, not repeated medians.

## Limits And Next Decision

This is a pilot, not a statistically powered benchmark. The model was not seeded,
arm execution order was not randomized, and repeat cases were selected after seeing
the first run. No faithfulness score is inferred from source coverage alone.

This also does not isolate whether an LLM is needed: Basic uses its existing cleaning
and size/page boundaries, while AI retains raw text and adds linked-unit expansion.
Larger, coherent passages may explain the benefit. A useful next ablation would compare
paragraph-aware cross-page grouping without an LLM at a similar source-token budget.

For now, preserve the experimental results, not an assertion that AI chunking solves
end-to-end answer quality. The current quote-based implementation still fails import,
and even the successful variant does not reliably produce faithful answers.

## Reproduce And Inspect

The local PDF, extracted pages, caches, SQLite indexes, and full answers remain under
`tmp/db50-comparison`, not in a distributed fixture. Full paired responses, source order,
rewrites, suggestions, and repeat responses are in `tmp/db50-comparison/answers.md`.
Machine-readable results are stored separately for each arm.

```sh
app_runtime/python/bin/python tests/experiments/compare_db50_preparation.py \
  --document /absolute/path/to/Database-System-Concepts-7th-Edition.pdf \
  --out tmp/db50-comparison-new --arm basic
app_runtime/python/bin/python tests/experiments/compare_db50_preparation.py \
  --document /absolute/path/to/Database-System-Concepts-7th-Edition.pdf \
  --out tmp/db50-comparison-new --arm ai
node tests/experiments/evaluate_document_answers.mjs \
  --input tmp/db50-comparison-new/basic/results.json \
  --out tmp/db50-comparison-new/basic/answers.json --organic
node tests/experiments/evaluate_document_answers.mjs \
  --input tmp/db50-comparison-new/ai/results.json \
  --out tmp/db50-comparison-new/ai/answers.json --organic
node tests/experiments/render_db50_report.mjs tmp/db50-comparison-new
```

These commands run the current production implementations, not the retired quote/prefix
experiments. The historical outputs remain under `tmp/db50-comparison`. Use a fresh
output directory for uncached timing.
The runtime and local models must already be installed. This experiment does not
download models or install dependencies automatically.

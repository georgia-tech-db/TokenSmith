# Advanced Math

## Settings and model

**Settings → Application → Advanced → Advanced Math** is off by default. It uses
only the local Ollama model `qwen2.5-coder:7b`, independently of the default chat
model. Legacy JavaScript settings and former experimental model selections are
ignored.

When the model is unavailable, Settings shows a disabled, unchecked switch and an
inline link to **Models**. Download, pause/resume and removal belong to the
**Ollama qwen2.5-Coder 7B** card, labeled **Math Model**, in **Your models**. The card
is absent from **Add local model**. Its disabled **Active Model** control identifies
the sole math model; it does not enable the setting or change the default chat model.
The download is approximately 4.7 GB; runtime context needs additional memory.

After installation, Settings explains that the local model generates and runs
JavaScript for multi-step calculations, then explains the results. Installation
does not automatically enable the feature. Opt-in persists across restarts.
Availability is checked on startup, app focus, navigation and model download changes.
A confirmed removal clears the saved opt-in. An offline server makes the feature
unavailable and keeps chat on the normal path without treating a connection failure
as proof of removal. Main-process dispatch independently checks model availability;
a missing model produces a clear error instead of silently substituting another model.

## Routing

The setting enables three-bucket answer planning:

- **Chat:** clear greetings, factual lookups, simple source counts, conceptual
  explanations and single-step arithmetic use the default model. These fast paths
  need no classifier call.
- **Math:** clear multi-step arithmetic, percentages, aggregation, formulas applied
  to data and repeated calculations use Qwen plus QuickJS. Routing determines
  computation intent, not the formula or expected answer. Requests to explain
  steps or formulas alongside applied calculation retain the math route;
  concept-only explanations remain on chat.
- **Ambiguous:** the default model classifies task intent. When conversation
  references already need resolution, classification shares that existing rewrite
  call. Otherwise an ambiguous request adds one call. Unclear tasks can return a
  clarification before retrieval or calculation.

The answer plan is reused at dispatch. Normal chat, practice tasks, suggested questions and simpler retellings keep
their existing paths. Practice tasks bypass Advanced Math. The shared rewrite
preserves main's separate native-reasoning decision alongside math routing.
Disabling the setting bypasses the JavaScript loop, even with a stale math-plan hint.

## Computation and explanation

1. Retrieve study context through the existing active materials, embeddings and
   search mode. The answer model's context budget determines source packing.
   Reference resolution retains the original question as the answer task; its
   rewritten query is only a retrieval aid.
2. Give Qwen one stable tool-aware prompt with a brief plan and a generic worked
   example. It returns raw JavaScript inside `<javascript_interpret>` tags,
   optionally fenced as JavaScript. Code is not transported as a JSON string.
3. Parse the first complete tool block and execute it in a fresh QuickJS runtime.
   Complete, explicitly JavaScript fences can be recovered if tool tags are
   missing, including a program split across fences. Prose and model-written
   feedback are never executed or accepted as execution output. Incomplete
   tagged calls still receive bounded repair feedback.
   Discard trailing speculative prose or further calls. Completion is currently
   non-streaming: discarded text has already been generated by Ollama.
4. Return execution output or a bounded error with its line, column and failing
   source line to the same model and conversation. Feedback uses labeled messages
   compatible with the installed Ollama template. Malformed blocks and runtime
   errors receive bounded repair attempts.
5. Missing or conflicting inputs may return a `<needs_information>` response
   instead of executing. Its clarification reaches the student with the same
   source citations, without repairs or another inference. Conditional numerical
   scenarios still use the tool. This decision belongs to the model, not a
   question-specific evidence parser.
   Input selection and the existing narration call both distinguish independent
   observations from incompatible versions of the same evidence. Versions must
   not be pooled to resolve a disagreement unless the student explicitly asks for
   that assumption. Independent observations retain their multiplicity: equal
   values are still separate observations unless distinct values are requested.
   After execution, phase-specific feedback asks the model to explain the completed
   output and retain the original evidence constraints. It does not repost the
   question or instruct the model to restart calculation. A
   clarification can replace an inappropriate computed result without another
   inference. Supported inputs omitted or altered by a program can instead
   trigger a replacement program within the existing retry budget; the model
   must not silently correct a result in prose.
6. Programs are prompted to print a generic teaching object with `method`,
   `inputs`, `steps` (substitution strings built from computed variables), and
   `results` (labeled, formatted values with units). This is output data, not a
   formula DSL or a source-review protocol. Plain console output remains
   supported; both `results` and the equivalent singular `result` field are
   recognized. Recognized teaching objects are checked for numeric consistency
   before their method, inputs, steps and results are formatted for feedback.
   Inconsistent printed teaching steps are withheld. Other steps are retained
   only after the remaining teaching data passes consistency checks again;
   result fields remain available for explanation or a bounded correction. No additional model pass
   is introduced.
   After success, the same model explains the method, substitutions, requested
   intermediate values, units and final result in Markdown. It is instructed to
   preserve executed values and avoid exposing JavaScript unless asked. Further
   tool corrections share the same attempt limit. An identical successful program
   reuses its result rather than executing again, and receives explicit no-progress
   feedback. If the model still repeats it at the limit, the response clearly labels
   its output as partial instead of claiming a complete answer. A different final
   correction withholds the previous result because it may be invalid. Empty narration falls
   back to executed output without another inference. For a valid teaching
   object, fallback presents the method, inputs, worked substitutions and results
   as instructional Markdown, without inventing a method or showing code. Numeric
   string arrays in plain output are displayed without JSON quotes. If a program
   omits teaching data, fallback cannot manufacture those missing steps.
7. Check narration for omitted/changed result numbers, reordered numeric arrays,
   unsupported numeric additions, explicit contradictions using output labels,
   and percentage/currency unit inconsistencies. Printed numbered labels are
   excluded from arithmetic operands only when they match execution labels;
   prose parentheses after an equation do not become arithmetic operands;
   assertions using those labels are checked against their printed result,
   including the final value in a substitution chain. Numeric equations, including
   supported KaTeX fractions, are checked in one additional bounded QuickJS
   execution, never host `eval`/`Function`. Math spans are separated from surrounding
   prose, including prose parentheses wrapping an equation. Result coverage excludes
   numbered labels and formula operands that are not displayed results; equivalent
   formula coefficients need not be repeated literally. For teaching objects,
   coverage checks use result fields rather than demanding every metadata number.
   Explicit trailing-zero precision is
   restored from output, and requested decimal precision is applied to displayed
   percentages without changing formula multipliers. A valid equality chain also supports its intermediate
   numeric operands, avoiding rejection of correct substitution steps just
   because they were not separately printed. No extra LLM call or review/repair inference is added;
   invalid narration falls back to readable execution details. Independently
   checked numerical substitutions from rejected narration may also be retained
   in fallback when their initial operands come from evidence, code, printed
   data or a previously checked intermediate. Incorrect equations and arbitrary
   prose are not retained. Explicit requested precision also formats fallback
   result values. Headings and
   explanation structure are not prescribed by validation.
8. Return citations for the packed passages actually supplied to Qwen. Mark the
   response **Advanced Math** and persist the actual answer model.

There is one computation path. The former JSON transport, arithmetic verifier,
source-selection review protocol, formula-specific fallbacks and duplicate router
have been removed. The narrow narration checks compare numeric claims with
execution/evidence; they do not independently select or verify the method.

## Limits and latency

QuickJS receives no filesystem, network, shell, process or Node APIs. Only bounded
`console.log` output is exposed from the host. Generated code is never passed to
host `eval` or `Function`. Every attempt disposes its runtime and context.

| Limit | Value |
| --- | ---: |
| Generated code | 8 KiB |
| Execution output | 8 KiB |
| Execution timeout | 1 second |
| Runtime memory | 16 MiB |
| Stack | 512 KiB |
| Repairs | 2 (3 total execution attempts) |

A normal successful calculation uses two Qwen inferences: code and explanation.
An information request can finish with one. Arithmetic narration validation is a
sandbox execution with the same limits; printed teaching equations may also be
checked before feedback. These checks do not consume a model
inference or the calculation's retry budget.
There is no extra review inference. Normal chat retains main's native reasoning
and prompt-preflight flow; these do not add calls to the Advanced Math loop. The dedicated profile uses an 8192-token
context, a 1536-token per-call output allowance, temperature 0, top-p 0.4, top-k 40,
min-p 0 and repeat penalty 1.18. Explicit settings for Qwen's model ID can customize
its profile; the loop retains its output allowance and temperature-zero override.
It does not inherit the default model's persona, endpoint or cloud credentials.

Local availability metadata is cached for 30 seconds when installed and 1 second
otherwise. Math context metadata is cached for five minutes, bounded to eight
entries and keyed by endpoint, model name and modification timestamp. Neither
model is forcibly preloaded.

`advanced_math_route`, `javascript_interpret`, `javascript_interpret_empty_response`
and `ollama_completion_usage` logs include routing, model selection, generated code,
execution result/error, retries, inference counts, inference/execution latency,
raw responses, discarded trailing text, recovered transport, unchanged corrections,
reused execution output, information requests,
narration issues, teaching output/consistency issues, omitted teaching steps,
validation latency and narration fallback. Request logs also
include context/routing and retrieval timing. Ollama loading, prompt-evaluation
and generation timing are recorded when supplied.

## Limitations

The earlier October 13 bounded acceptance run, before the structured teaching
handoff, did **not** clear the merge gate. All seven
computable cases returned correct final aggregates, but only six included every
requested numeric result and only three retained full teaching narration. Four
used fallback after narration errors. Missing source inputs were handled safely;
conflicting source versions were incorrectly pooled. Two ordinary-chat checks
stayed on the default model. This was one run per case with supplied source
fixtures, not a controlled benchmark or live retrieval evaluation. The feature
remains draft pending generic output-completeness and evidence-selection work.

Successful execution proves what the generated program computed. It does not prove
that the model chose the right textbook passage, inputs, population, formula,
denominator or units. Narration checks catch supported numeric contradictions;
they do not prove arbitrary prose, equivalence of differently named concepts,
value-to-label associations or every possible unit conversion. Source consistency
and population selection still rely on the model. Asking it to reconsider these
in the narration call improves the feedback flow, not a formal guarantee.
Unsupported or
uncheckable numeric explanations may use the deterministic fallback.
Routing is also fallible. Missing evidence can still be mishandled by the model;
there is no independent semantic verifier in this path. The five manual Qwen cases
are preliminary evidence, not general accuracy certification. Earlier PR benchmark
results belong to an older verifier-based implementation and do not certify this
Advanced Math loop.
